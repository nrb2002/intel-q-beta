# Database Design

## Intel-Q Queue Management System

**Version:** 1.0
**Database:** PostgreSQL
**ORM:** Prisma
**Last Updated:** July 2026

---

# Overview

Intel-Q uses **PostgreSQL** as its primary database to store users, queue tickets, and branch information. PostgreSQL was selected because it provides strong data integrity, structured relational data modeling, reliable transactions, and excellent support for relationships between customers, queue tickets, and organization branches.

The initial MVP focuses on three core data entities:

* Users
* Queue Tickets
* Branches

This design satisfies the application's current requirements while allowing future expansion.

The database is accessed through **Prisma ORM**, which provides type-safe database queries, schema management, migrations, and strong integration with the Next.js and TypeScript application.

# Database Schema

Intel-Q uses three primary database models:

- User
- QueueTicket
- Branch

The models are related using Prisma relations, which generate PostgreSQL foreign key constraints to maintain referential integrity.

```text
User (1)
    │
    │ customerId
    │
    └───────────< QueueTicket (*) >───────────┐
                                               │
                                               │ branchId
                                               │
                                           Branch (1)
```

## Relationships

### User → QueueTicket

**Relationship:** One-to-Many

A user (customer) may create multiple queue tickets over time.

Each queue ticket references exactly one customer through the `customerId` foreign key.

```text
QueueTicket.customerId
        ↓
User.id
```

---

### Branch → QueueTicket

**Relationship:** One-to-Many

Each branch manages many queue tickets.

Every queue ticket belongs to exactly one branch through the `branchId` foreign key.

```text
QueueTicket.branchId
        ↓
Branch.id
```

---

## Referential Integrity

The database enforces referential integrity using PostgreSQL foreign keys generated from the Prisma schema.

This ensures that:

- A queue ticket cannot reference a user that does not exist.
- A queue ticket cannot reference a branch that does not exist.
- Users and branches with existing queue tickets cannot be deleted accidentally without first addressing their related queue records.

These constraints help maintain consistent and reliable queue data throughout the application.

# Core Data Models

## User

The `User` model stores application users, including customers, staff members, and administrators.

### Fields

| Field        | Prisma Type   | Required | Description                           |
| ------------ | ------------- | -------- | ------------------------------------- |
| id           | String        | Yes      | Unique identifier generated by Prisma |
| firstName    | String        | Yes      | User's first name                     |
| lastName     | String        | Yes      | User's last name                      |
| email        | String        | Yes      | Unique email address                  |
| password     | String        | Yes      | Hashed password                       |
| role         | UserRole      | Yes      | Customer, staff, or administrator     |
| createdAt    | DateTime      | Yes      | Account creation date                 |
| updatedAt    | DateTime      | Yes      | Last profile update                   |
| queueTickets | QueueTicket[] | No       | Queue tickets created by the customer |

### User Roles

The application supports the following roles:

* `CUSTOMER`
* `STAFF`
* `ADMIN`

The role should be implemented using a Prisma enum.

Example:

```prisma
enum UserRole {
  CUSTOMER
  STAFF
  ADMIN
}
```

### Validation Rules

* Email must be unique.
* Email should be stored in lowercase.
* First name is required.
* Last name is required.
* Password is required for credential-based authentication.
* Passwords must be securely hashed before storage.
* Role must be one of the supported `UserRole` values.
* Users should not be permanently deleted during the MVP unless required by an administrator.

# Queue Ticket

The `QueueTicket` model represents a customer waiting for or receiving service at a branch.

### Fields

| Field        | Prisma Type | Required | Description                                   |
| ------------ | ----------- | -------- | --------------------------------------------- |
| id           | String      | Yes      | Unique queue ticket identifier                |
| ticketNumber | Int         | Yes      | Queue ticket number displayed to the customer |
| customerId   | String      | Yes      | Foreign key referencing User                  |
| branchId     | String      | Yes      | Foreign key referencing Branch                |
| serviceType  | String      | Yes      | Type of service requested                     |
| status       | QueueStatus | Yes      | Current queue ticket status                   |
| createdAt    | DateTime    | Yes      | Ticket creation time                          |
| calledAt     | DateTime    | No       | Time customer was called for service          |
| completedAt  | DateTime    | No       | Time service was completed                    |
| customer     | User        | Yes      | Related customer                              |
| branch       | Branch      | Yes      | Related branch                                |

### Queue Status

The queue ticket status should be implemented using a Prisma enum.

```prisma
enum QueueStatus {
  WAITING
  IN_SERVICE
  COMPLETED
  CANCELLED
}
```

### Validation Rules

* Ticket number is required.
* Customer reference is required.
* Branch reference is required.
* Service type is required.
* Status is required.
* Status must be one of:

  * `WAITING`
  * `IN_SERVICE`
  * `COMPLETED`
  * `CANCELLED`
* `calledAt` should be populated when a ticket changes to `IN_SERVICE`.
* `completedAt` should be populated when a ticket changes to `COMPLETED`.
* A completed or cancelled ticket should not appear in the active queue.
* Queue tickets should not be permanently deleted during normal operations unless deletion is explicitly required by the application workflow.

# Branch

The `Branch` model stores information about organization branches where customers receive services.

### Fields

| Field        | Prisma Type   | Required | Description                         |
| ------------ | ------------- | -------- | ----------------------------------- |
| id           | String        | Yes      | Unique branch identifier            |
| name         | String        | Yes      | Branch name                         |
| address      | String        | Yes      | Branch physical address             |
| city         | String        | Yes      | Branch city                         |
| createdAt    | DateTime      | Yes      | Branch creation date                |
| updatedAt    | DateTime      | Yes      | Last branch modification            |
| queueTickets | QueueTicket[] | No       | Queue tickets managed by the branch |

### Validation Rules

* Branch name is required.
* Address is required.
* City is required.
* Branch information must be validated before creation or update.
* Duplicate branch records should be prevented where appropriate.
* Branches should preferably be deactivated rather than permanently deleted once they have associated queue history.

# Prisma Schema Design

The following represents the core structure that should be implemented in `prisma/schema.prisma`.

```prisma
enum UserRole {
  CUSTOMER
  STAFF
  ADMIN
}

enum QueueStatus {
  WAITING
  IN_SERVICE
  COMPLETED
  CANCELLED
}

model User {
  id           String        @id @default(cuid())
  firstName    String
  lastName     String
  email        String        @unique
  password     String
  role         UserRole      @default(CUSTOMER)
  createdAt    DateTime      @default(now())
  updatedAt    DateTime      @updatedAt

  queueTickets QueueTicket[]
}

model QueueTicket {
  id          String      @id @default(cuid())
  ticketNumber Int
  customerId  String
  branchId    String
  serviceType String
  status      QueueStatus @default(WAITING)
  createdAt   DateTime    @default(now())
  calledAt    DateTime?
  completedAt DateTime?

  customer    User        @relation(fields: [customerId], references: [id])
  branch      Branch      @relation(fields: [branchId], references: [id])

  @@index([customerId])
  @@index([branchId])
  @@index([status])
  @@index([branchId, status])
}

model Branch {
  id           String        @id @default(cuid())
  name         String
  address      String
  city         String
  createdAt    DateTime      @default(now())
  updatedAt    DateTime      @updatedAt

  queueTickets QueueTicket[]

  @@index([name])
}
```

> **Note:** The Prisma schema above is the starting point for the MVP. Additional constraints, indexes, and fields may be introduced as the application implementation develops.

# Referential Integrity

PostgreSQL foreign keys and Prisma relationships should be used to maintain data integrity.

The following relationships must be enforced:

```text
QueueTicket.customerId
        ↓
User.id
```

```text
QueueTicket.branchId
        ↓
Branch.id
```

A queue ticket cannot reference a customer or branch that does not exist.

For the MVP, deletion behavior should protect historical queue data. Users and branches with existing queue tickets should not be permanently deleted without an intentional data-management strategy.

# Indexing Strategy

The following indexes should be created to improve common query performance.

## Users

### Unique Email

```text
email
```

The email field must have a unique constraint because it is used for authentication.

---

## Queue Tickets

Recommended indexes:

```text
customerId
branchId
status
branchId + status
```

The combined `branchId` and `status` index is particularly useful when retrieving active queue tickets for a specific branch.

Example query:

```text
Find all WAITING tickets for Branch A
```

This is a common operation for staff dashboards.

---

## Branches

Recommended index:

```text
name
```

This supports branch lookup and search operations.

# Data Lifecycle

## User

```text
Create
   ↓
Authenticate
   ↓
Active
   ↓
Update Profile
```

Users are not permanently deleted during the MVP.

Future versions may support account deactivation or administrative user management.

---

## Queue Ticket

```text
WAITING
   ↓
IN_SERVICE
   ↓
COMPLETED
```

A ticket may also be cancelled:

```text
WAITING
   ↓
CANCELLED
```

The complete lifecycle is:

```text
                 ┌──────────────┐
                 │   WAITING    │
                 └──────┬───────┘
                        │
              ┌─────────┴─────────┐
              │                   │
              ▼                   ▼
      ┌──────────────┐    ┌──────────────┐
      │  IN_SERVICE  │    │  CANCELLED   │
      └──────┬───────┘    └──────────────┘
             │
             ▼
      ┌──────────────┐
      │  COMPLETED   │
      └──────────────┘
```

Completed and cancelled tickets should remain in the database for historical records during the MVP.

Future versions may introduce a dedicated queue history or archival strategy.

---

## Branch

```text
Create
   ↓
Active
   ↓
Update
   ↓
Deactivate
```

Branch deactivation is a future enhancement.

For the MVP, branches should not be permanently deleted if they have associated queue ticket history.

# Database Environment Configuration

The application should use an environment variable for the PostgreSQL connection.

Example:

```env
DATABASE_URL="postgresql://username:password@localhost:5432/intel_q"
```

The actual credentials must never be committed to GitHub.

The `.env.local` file should remain excluded from version control.

The project should provide a `.env.example` file containing the required environment variable names without exposing real credentials.

Example:

```env
DATABASE_URL="postgresql://username:password@localhost:5432/intel_q"
AUTH_SECRET="your-secret-key"
AUTH_URL="http://localhost:3000"
```

---

# Prisma Configuration

Prisma should be used as the application's primary database access layer.

The main Prisma schema should be located at:

```text
prisma/schema.prisma
```

The Prisma Client should be generated from the schema and used for type-safe database operations.

A shared Prisma Client instance should be used to avoid creating excessive database connections during Next.js development and hot reloading.

Recommended application structure:

```text
prisma/
└── schema.prisma

src/
└── lib/
    └── prisma.ts
```

---

# Database Migrations

Database changes must be managed through Prisma migrations.

During development, use:

```bash
npx prisma migrate dev
```

Generate Prisma Client when required:

```bash
npx prisma generate
```

To inspect the database using Prisma Studio:

```bash
npx prisma studio
```

Before deploying schema changes to production, migrations should be applied using the appropriate production migration command.

```bash
npx prisma migrate deploy
```

Database migrations must be reviewed through Pull Requests before being merged into the main branch.

# Database Access Guidelines

All database operations should be performed on the server.

Database access should occur through:

* Next.js Route Handlers
* Server Actions
* Server-side service functions

Client components should never directly connect to PostgreSQL or Prisma.

The general request flow should be:

```text
Client Component
       │
       ▼
Next.js Route Handler / Server Action
       │
       ▼
Service or Server Logic
       │
       ▼
Prisma Client
       │
       ▼
PostgreSQL
```

This architecture protects database credentials and keeps sensitive business logic on the server.

Install Prisma and the Prisma Client:

```bash
npm install prisma @prisma/client
```

Initialize Prisma:

```bash
npx prisma init
```

```text
.env.local
```

```env

```

---

Create or update:

```text

```

Define:

* `User`
* `QueueTicket`
* `Branch`
* `UserRole`
* `QueueStatus`

Run:

```bash
npx prisma migrate dev --name init
```

Run:

```bash
npx prisma generate
```

---

## Step 6 — Create Prisma Client Utility

Create:

```text
src/lib/prisma.ts
```

Configure a shared Prisma Client instance for server-side database operations.

Create server-side functions for operations such as:


Verify that:

The database implementation is considered complete when:

* PostgreSQL is configured and accessible.
* Prisma is installed and configured.
* `prisma/schema.prisma` contains the core models.
* User, QueueTicket, and Branch models are implemented.
* User roles are defined.
* Queue ticket statuses are defined.
* Foreign-key relationships are working.
* Prisma migrations run successfully.
* Prisma Client generates successfully.
* Database operations are type-safe.

* Indexes and unique constraints are configured.

# Design Principles

The database design follows these principles:

* Keep database models simple and focused.
* Use PostgreSQL relationships and foreign keys to maintain data integrity.
* Use Prisma for type-safe database access.
* Validate data at both the application and database levels where appropriate.
* Use migrations to track schema changes.
* Protect sensitive user and authentication information.
* Keep database operations on the server.
* Avoid unnecessary duplication of data.
* Preserve historical queue information where possible.
* Support future scalability without over-engineering the MVP.
* Keep business logic in server-side services, Route Handlers, and Server Actions rather than embedding unnecessary business logic in the database.

---

# Summary

The Intel-Q database consists of three primary models—**User, QueueTicket, and Branch**—which provide the foundation for authentication, queue management, and organizational structure.

PostgreSQL provides the relational structure and data integrity required to connect customers, queue tickets, and branches. Prisma provides type-safe access to the database and simplifies schema management, migrations, and database operations within the Next.js and TypeScript application.

This design aligns with the Intel-Q MVP goals while remaining flexible for future enhancements such as appointments, service counters, notifications, analytics, audit logs, and multi-organization support.
